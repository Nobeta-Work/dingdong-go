# 叮咚商城 Go Demo PRD

版本：v1.0  
日期：2026-10-24  
用途：可独立复制到新仓库，作为后端 Demo 产品需求、架构约束及验收依据。本文不依赖原工作区文件。所有验收数字均为目标，不能视为已经实现或实测。

## 1. 产品目标

实现一个面向限量活动销售的商城：用户浏览活动、提交抢购、查询成单结果并完成模拟支付；未支付订单自动关闭并释放库存。运营可以创建活动、查看订单与活动进度。

Demo 必须能实际运行完整链路，重点展示三项能力：

1. 热点活动查询：Redis 缓存与 singleflight 合并回源。
2. 抢购异步成单：限流、额度准入、持久化受理、MQ 消费及库存约束。
3. 支付与超时关单：处理重复通知、迟到结果和库存确认/释放。

采用完整 Go 微服务架构；核心开发范围为交易服务，上下游实现最小但真实的业务能力。最终交付不得用内存假订单或固定成功的库存接口代替持久化闭环。复用原 Java 商城的 Vue 项目，本 PRD 只包含后端开发；既有前端作为接口兼容性参考，不新增或修改前端模块。

## 4. 后端接入与接口兼容

复用既有 Java 商城的 Vue 项目，不开发页面、前端组件、前端工程或前端部署模块。

- 开发前读取既有前端的 API 封装与 Java 接口契约，对齐路径、请求字段、响应结构、分页、鉴权头、业务错误码及状态枚举。
- 第7节接口为后端业务契约基线；与既有前端存在差异时，在后端 HTTP 适配层映射，记录对应关系，不要求重写前端。
- 既有前端或接口资料暂不可得时，先按本文契约交付可执行接口脚本，并明确兼容性待验证，不宣称已完成前端联调。
- 抢购接口区分未受理、已受理、已成单与最终失败；查询返回 requestId、orderNo、处理状态和失败原因。轮询超时不改变业务状态。
- 订单接口返回商品快照、金额、expiresAt、订单状态及库存确认状态；支付接口明确为模拟支付，不产生真实扣款。
- 运营能力仅交付鉴权后的管理接口及调用示例，不开发运营页面。
- 后端验收使用 HTTP/RPC 调用脚本、数据库不变量检查及日志指标，不依赖浏览器操作。
## 5. 业务规则

1. 首版单活动对应单 SKU，数量固定 1，每个用户在同一活动最多生成一张订单。
2. 成单前最终失败可释放用户资格；之后用户可使用新 requestId 再尝试。同一旧 requestId 永远返回其原失败结果。
3. 已生成订单即消耗活动资格，即使超时取消也不返还活动额度或允许用户再抢；只释放真实 SKU 库存。活动接口返回该规则说明。
4. 活动额度是准入预算，数据库 SKU 库存为最终可售依据；准入成功不保证成单。
5. 发布后冻结 SKU、活动价格、额度、开始/结束时间。Demo 不实现在线修改这些交易字段；展示文案可修改并失效缓存。
6. 用户提交时以数据库活动配置校验可受理状态并记录版本。异步消费时依据已受理快照成单，不能因排队跨过活动结束时间而拒绝合法受理。
7. 支付窗口从订单创建时计算，默认 120 秒，可配置；不因客户端重复查询而重新计时。
8. 金额用人民币“分”的 int64 存储，JSON 中业务 ID 使用字符串，避免 JavaScript 大整数精度问题。
9. 所有时间落库为统一时区的时间戳，API 使用带时区 ISO 8601；客户端按需转换显示。
10. 发布额度不得大于发布时可用库存，但这不替代成单时的原子库存检查。首版种子活动使用不同 SKU，避免无意共享库存干扰演示。

## 6. 服务架构与所有权

| 服务 | 对外能力 | 数据所有权 |
|---|---|---|
| user-service | 登录、当前用户 | 用户、角色 |
| catalog-service | 商品查询；库存预占、查询、确认、释放 | SKU、库存、预占流水 |
| trade-service | 活动、抢购受理、订单、支付编排、消费者及补偿 | 活动、受理、资格、订单、Outbox、任务 |
| payment-service | 模拟支付单创建/查询/关闭、模拟支付确认、支付结果事件 | 支付单、支付 Outbox |

技术栈：Go、Gin、grpc-go、Protobuf、database/sql、MySQL、go-redis、Redis Lua、RocketMQ、Docker Compose、Kubernetes、Traefik。

- Gin 负责 HTTP 路由、绑定与中间件；内部同步调用使用 gRPC。
- HTTP Handler、RPC Handler、MQ Consumer 调用业务层，共用事务和业务规则，不通过网络调用自身接口。
- 各服务独立数据库权限；Demo 可共用一个 MySQL 实例的四个逻辑库，不跨库写表或做跨服务 SQL JOIN。
- 业务事件通过 MQ 传播；Outbox 与业务状态在所属服务本地事务提交。
- 不建立纯转发的自研 API 网关。入口按路径路由到对应 HTTP 服务。
- gRPC ClientConn 长期复用；调用有 deadline，未知结果按业务键回查。默认不对所有写操作透明重试。
- RPC 仅部署于内部网络；对外只暴露必需 HTTP 路径。客户端提供的身份头不直接作为可信身份。

## 7. HTTP 与 RPC 契约

### 7.1 HTTP

统一响应包含 code、message、data、traceId；错误码与业务终态稳定。读取不存在对象返回 404；无身份 401，无权限 403；规则冲突 409；参数错误 400；限流 429；依赖不可用 503。

| 方法与路径 | 功能 | 关键要求 |
|---|---|---|
| POST /api/auth/login | 登录 | 返回 accessToken、过期时间与用户信息 |
| GET /api/auth/me | 当前用户 | 验证 JWT |
| GET /api/activities | 活动列表 | 分页、活动状态 |
| GET /api/activities/{id} | 活动详情 | 公共展示缓存，不混入用户资格 |
| GET /api/activities/{id}/participation | 当前用户参与状态 | 当前 requestId、orderNo、结果；鉴权 |
| POST /api/activities/{id}/requests | 提交抢购 | body: requestId；数量固定1；新受理202，重复请求返回已有状态 |
| GET /api/requests/{requestId} | 查询受理结果 | 仅请求所属用户可读 |
| GET /api/orders | 我的订单 | 分页，按当前用户过滤 |
| GET /api/orders/{orderNo} | 订单详情 | 检查归属，含支付截止与库存确认状态 |
| POST /api/orders/{orderNo}/payment | 创建/获取支付单 | 交易服务验证归属与订单状态后调用支付 RPC |
| POST /api/payments/{paymentNo}/simulate-success | 模拟支付确认 | 支付服务检查归属、终态和截止时间，不接受客户端金额 |
| GET /api/payments/{paymentNo} | 查询模拟支付结果 | 仅所属用户可读 |
| POST /api/admin/activities | 新建活动草稿 | 运营权限 |
| POST /api/admin/activities/{id}/publish | 发布活动 | 幂等，初始化完成后开放 |
| POST /api/admin/activities/{id}/pause | 暂停新受理 | 数据库校验为准 |
| GET /api/admin/activities/{id}/stats | 活动统计 | 给出统计时间，区分处理中与失败 |

### 7.2 最小 RPC

| 服务 | 方法 | 关键字段 |
|---|---|---|
| Catalog | GetSKU | skuId、名称、价格、可用状态 |
| Inventory | Reserve / GetReservation / Confirm / Release | orderNo、skuId、quantity、预占状态 |
| Payment | CreateOrGet / QueryByOrder / CloseByOrder | orderNo、userId、amountCent、expiresAt、支付终态 |

CreateOrGet 必须校验同 orderNo 的金额、用户等参数一致。CloseByOrder 即使支付单尚不存在，也要创建关闭标记，阻止迟到的 CreateOrGet 再创建可支付记录。库存 Release 同样需要处理“释放先到、预占后到”的情况。

Protobuf 字段编号稳定，删除字段保留编号。缺货等业务拒绝与网络超时必须可区分；错误不得全部压成 Internal。

## 8. 状态机与数据模型

### 8.1 状态

| 对象 | 状态与转换 |
|---|---|
| 活动 | DRAFT → PUBLISHING → PUBLISHED；PUBLISHED → PAUSED；未开始/进行中/已结束根据时间计算 |
| 受理请求 | ACCEPTED → PROCESSING → ORDER_CREATED 或 FAILED；PROCESSING 可被恢复任务继续，不因超时直接失败 |
| 用户活动资格 | AVAILABLE → HELD → CONSUMED；成单前失败可由 HELD 回 AVAILABLE；持有者为 requestId |
| 订单 | PENDING_PAYMENT → PAID；PENDING_PAYMENT → CLOSING → PAID 或 CANCELED |
| 库存预占 | LOCKED → CONFIRMED 或 RELEASED；允许先落 RELEASED 终止标记阻止迟到预占 |
| 支付 | PENDING → SUCCESS 或 CLOSED；不存在时允许 CloseByOrder 落 CLOSED；终态互斥 |

数据库内的用户活动资格表以 activityId+userId 唯一，转换必须校验当前持有 requestId；终止请求不能释放另一请求的资格。订单另设 activityId+userId 唯一，确保最多一张订单。受理历史允许多条失败记录，不对全部历史受理简单设置 activityId+userId 唯一。

### 8.2 最小表

| 所属库 | 表与关键字段/约束 |
|---|---|
| user | users：账号唯一、密码哈希、角色 |
| catalog | sku、inventory：总量/available/locked/sold；库存不得为负 |
| catalog | inventory_reservation：orderNo+skuId 唯一、数量、状态 |
| trade | activity：SKU 快照、价格、额度、时间、版本、发布状态 |
| trade | activity_request：userId+requestId 唯一、参数摘要、activityId、稳定 orderNo、状态、失败原因 |
| trade | activity_participation：activityId+userId 唯一、holderRequestId、状态 |
| trade | orders/order_items：orderNo 唯一、activityId+userId 唯一、金额快照、expiresAt、状态、库存确认标记 |
| 各事件生产库 | outbox：eventId 唯一、聚合ID、类型、payload、重试时间、状态 |
| trade | operation_task：业务键、动作、下一次执行时间、尝试次数、处理状态 |
| payment | payment：orderNo 唯一、paymentNo、userId、金额、expiresAt、状态 |

到期扫描建立 status+expiresAt 索引，Outbox 扫描建立 status+nextAttemptAt 索引。多实例任务采用条件抢占或数据库行锁领取；网络调用放在短事务之外。租约仅控制领取，并不能替代终态条件更新与业务幂等。

## 9. 核心流程与故障规则

### 9.1 发布与缓存

发布先落 PUBLISHING，幂等初始化活动配置/额度，再切为 PUBLISHED。未完成初始化的活动不接受请求；失败可重试，不重复设置初始额度。运行中重建缓存不得覆盖已消耗额度。

活动详情采用 Cache-Aside，正常 TTL 初始 60 秒并加抖动，空值 TTL 初始 5 秒。singleflight 合并实例内同 key 回源，执行者二次检查缓存。共享加载使用有界服务上下文，单个等待者取消不取消其他等待者。限制不同 key 的总回源并发。

展示更新先提交数据库后失效缓存，失败持久化重试；接受短暂陈旧，交易校验不能依赖展示缓存。Redis 故障时普通查询只在本地并发预算内回源。

### 9.2 抢购与成单

1. 验证用户和 requestId；已持久化的重复请求直接返回既有结果，不重新扣额度。相同 ID 参数不同返回409。
2. Gin 中间件通过 Redis Lua 令牌桶控制用户+接口与活动总速率。被拒绝返回429，不执行准入。
3. 准入 Lua 校验活动缓存配置、额度和用户资格，原子写预扣记录；包含 requestId、时间和归属。相关键采用同一活动 hash tag。
4. 数据库本地事务校验可受理活动及版本、持有用户资格、写受理快照和成单 Outbox；提交成功才返回202。
5. 投递器发送成单事件；消费者使用稳定 orderNo 预占库存，然后本地事务创建订单、快照、到期事件并将受理设为 ORDER_CREATED、资格设为 CONSUMED。
6. 最终业务失败先可靠落 FAILED，再幂等释放 Redis 准入额度与资格；库存预占结果未知时先回查，不提前失败回补。

跨服务事务不使用 Seata。库存修改与库存流水在 catalog 本地事务完成；交易状态与事件在 trade 本地事务完成。

预扣成功但受理事务未完成：保留 Redis 预扣索引，由重试或扫描恢复。决定终止前以同业务键在数据库落失败记录，和迟到受理竞争；终止成功后才回补。不能只设置 Redis TTL 后忘记恢复额度。

Redis 状态丢失：暂停新受理，通过数据库中持久化请求、资格和订单重建后再开放；已返回202的请求必须能继续处理。对于未持久化预扣，利用活动恢复期间的准入代次/栅栏校验拒绝旧在途受理，避免重建额度后旧请求再落库。实现需要明确选择并验证该栅栏方案，不允许直接覆盖初始库存后继续接单。

### 9.3 支付与关闭

- 创建支付单前交易服务校验归属、订单状态；支付端独立校验 expiresAt，拒绝过期支付确认。
- 模拟支付成功：支付状态与成功 Outbox 同事务提交；订单消费事件后更新 PAID，并同事务写库存确认事件。
- 超时事件只是提醒，重新核对 expiresAt；进入 CLOSING 后 QueryByOrder，再按结果调用 CloseByOrder。
- 已成功则转 PAID；支付侧确认 CLOSED 后才转 CANCELED，并产生库存释放事件。
- 关闭结果未知时保留 CLOSING 和库存，继续回查，不能假定关闭成功。
- PAID 与库存确认完成分别记录；未确认库存不得返回可履约状态。重复支付事件不能跳过尚未完成的库存动作。
- 延时事件之外每5秒扫描到期订单作为 Demo 兜底，分页处理，不能一次全表加载。

### 9.4 MQ 与任务

统一事件包含 eventId、eventType、aggregateId、occurredAt、schemaVersion、payload、traceId。至少包含 CreateOrderRequested、PaymentSucceeded、InventoryConfirmRequested、InventoryReleaseRequested、OrderExpiryDue。

Outbox 发送成功前退出可能重发；消费者不得依赖消息只投递一次。技术失败有限退避重试并保留可恢复记录，业务拒绝落终态。达到自动重试阈值的任务可标记 NEEDS_REVIEW，但必须可查看并恢复，不得丢弃或伪装为成功。

RocketMQ 版本、Go 客户端、是否需要 Proxy、延时消息能力必须在依赖清单中配套固定；先验证最小生产/消费/重投链路，再开发业务。不得以不兼容的 SDK/API 拼出无法启动的环境。

## 10. 限流与默认运行参数

| 参数 | Demo 初始值/要求 |
|---|---|
| 用户抢购令牌桶 | 容量3，补充1 token/s |
| 活动总令牌桶 | 容量500，补充100 token/s；可通过配置调整 |
| 支付窗口 | 120秒；测试允许缩短 |
| 建议客户端受理轮询 | 1秒间隔，连续30秒后转手动刷新 |
| RPC 超时 | 库存/支付初始1秒，按实测调整并受上游预算约束 |
| 消费并发 | 初始8，结合数据库连接池预算配置 |
| 到期/补偿扫描 | 初始5秒，批量100；有任务领取与并发上限 |

令牌桶使用 Redis 时间，脚本原子补充、扣减并设置合理过期时间；桶过期不能早于其补满周期。用户桶与活动桶分别扣减，不承诺跨桶原子；后一桶拒绝不回退前一桶的速率预算。

Redis 故障时抢购返回503，不无条件放行。令牌桶、活动额度与数据库库存各自负责流量、准入和最终可售量；不能用同一个“库存不足”提示掩盖三种拒绝原因。

## 11. 开发与部署

### 11.1 Compose

- 提供四个 Go 服务、MySQL、Redis、RocketMQ 所需组件的 Compose 配置，不包含前端容器。
- 服务使用同一网络内 DNS 名访问，如 dns:///catalog-service:9000；不写死 IP。
- 宿主机 IDE 调试使用暴露端口，如 dns:///localhost:19000；提供对应配置示例。
- 提供后端 HTTP 端口及可选统一反向代理入口；接口脚本使用可配置 API_BASE_URL。按既有 Vue 项目的请求方式配置 CORS 或代理路径，明确允许的来源。
- 提供迁移、初始化和健康检查；依赖未就绪需明确提示或有界重试。
- 镜像、Go 工具链、SDK 固定兼容版本，不使用无约束 latest。README 给出经实际验证的环境资源和启动命令。

### 11.2 K8s

- HTTP 入口：Traefik + 标准 Ingress，按 /api/auth、/api/activities、/api/orders、/api/payments 等路由，包含受理、运营路径；不部署前端资源。
- HTTP Service 使用 ClusterIP；内部 RPC 使用 selector 选择 Pod 的 Headless Service，clusterIP: None。
- grpc-go 配置 DNS resolver 和 round_robin；Headless 仅提供实例发现，不承担请求转发。
- 提供命名空间、Deployment、Service、ConfigMap、Secret 示例引用、探针、requests/limits。
- readiness 与 liveness 分离；共享依赖短暂故障不能触发所有 Pod 无限重启。
- 处理 SIGTERM：标记未就绪、停止领取新任务、停止拉取新消息、排空 HTTP/gRPC 在途工作，最后关闭连接；超出排空期限才强制停止。
- 未完成消费不确认，重投后幂等；终止宽限期覆盖排空预算。
- 数据库与 MQ 可接外部 Demo 实例，明确连接方式；不要求编写生产级有状态集群部署。
- 不安装 Istio，不叠加独立注册中心，不使用已退休的社区 ingress-nginx。Gateway API/HPA 只列后续选项。

## 12. 可观测性与诊断

提供结构化日志和指标，至少包含：

- traceId、requestId、orderNo、eventId、服务名、实例名、错误类别。
- 请求量、延迟、429/503 数量，RPC 失败与超时。
- 缓存命中、实际数据库回源次数、singleflight 合并情况。
- 受理/成单/失败数量，未完成请求年龄，Outbox 积压与重试。
- 支付/关闭状态、库存确认与释放失败、未收敛任务数。

诊断脚本能输出订单、支付、库存流水的一致性结果；接口返回“成功”不是唯一验收依据。故障注入仅在 Demo/测试配置开启，需运营鉴权或仅内部可达，不提供匿名公开开关。

## 13. 验收标准

### 13.1 基础流程

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A01 | 干净环境启动与种子初始化 | README 命令可执行，后端接口及依赖就绪；重复初始化不重复建活动/重置运行中额度 |
| A02 | 登录与权限 | 用户不可查询/支付他人订单，普通用户不可管理活动 |
| A03 | 正常抢购与支付 | 受理→成单→支付成功→库存确认；接口返回、订单、支付与流水一致 |
| A04 | 不付款 | 截止后自动核对并关闭，库存释放一次，用户资格不恢复 |
| A05 | 请求重放 | 同requestId返回同结果；换参数409；同用户换ID不重复成单 |
| A06 | 服务重启 | 持久化的受理、订单与未完成任务能恢复，不依赖内存状态 |

### 13.2 缓存、并发与限流

- 缓存：双交易实例，各50个请求访问同一个有效活动，一次失效窗口、无故障/重试；统计活动主查询不超过2次。定向实例发压保证分布，不把随机负载分配误当实验前提。
- 正确性：200件库存、500个独立用户各提交1次。固定足够的限流突发容量并保证压测令牌有效；健康且无其他竞争时最终应有200张订单，其余得到明确拒绝/失败，不得永久处理中。
- 约束：任何时刻库存不为负；available+locked+sold等于初始库存；每用户每活动最多一张订单；确认与释放互斥。
- 单独限流测试：固定容量与补充速率，验证突发、持续请求、多实例共享预算与429；不以大量限流造成的低成单量证明库存正确。
- 记录受理率、处理时延和未收敛数，不将并发500写成QPS500，不预设吞吐提升倍数。

### 13.3 故障回归

以下8类各至少5组，共40组；每组保存注入位置、时间、操作步骤及最终不变量结果。

1. 重复支付成功事件：订单和库存只确认一次。
2. 支付已成功但通知延迟：超时流程查出成功，不误关单。
3. 关闭先成功、支付确认后到：支付保持CLOSED，不产生成功扣款事实。
4. 关单响应丢失：回查确认后关闭，未知期间不提前释放。
5. 库存确认失败：订单可已支付，但履约标记等待；恢复后确认一次。
6. 库存释放失败：保留恢复任务，最终释放一次。
7. 消费者/服务退出：未确认消息重投，已提交结果不重复执行。
8. 消息乱序：库存先释放后迟到预占、重复超时事件等不破坏终态。

另补关键窗口测试：预扣后落库前退出、MQ已收但发送响应丢失、支付单创建与关闭并发、Redis重建与旧在途请求竞争。测试环境恢复健康后，普通补偿目标30秒内完成；超出则输出待处理任务并判失败，不静默忽略。

### 13.4 K8s

- 两个库存副本均能处理连续 RPC，输出实际 Pod 名；不要求严格各半。
- 扩缩容后记录解析/连接收敛过程，不能宣称即时均匀分流。
- 交易滚动更新时记录请求成功/失败、消息重投、重复订单和未完成任务；退出后已受理工作能够恢复。
- readiness 排除不就绪实例；liveness 不因数据库短时不可用造成重启风暴。
- 所有性能与部署结果注明机器资源、组件版本、配置及样本，不预写“零失败”。

## 14. 交付物与启动体验

建议使用一个仓库、一个 Go module，按 cmd/user、cmd/catalog、cmd/trade、cmd/payment 构建四个二进制；服务业务分别放 internal 下对应目录。公共包仅包含协议、日志和基础工具，不能用共享业务包跨服务直接写表。

必须交付：

1. Go 服务源码、Protobuf 源文件与生成命令。
2. 数据库迁移、种子脚本、配置示例和依赖版本清单。
3. Compose 配置、K8s/Traefik 清单及启动/停止/排障 README。
4. HTTP API 文档、错误码、主要状态转换说明及既有 Vue 接口兼容映射。
5. 并发与故障测试脚本、验证不变量的脚本、实际运行报告。
6. 一套可执行后端演示脚本：启动→登录→抢购→支付→查询结果；另有不支付自动关闭的脚本。

README 必须说明哪些命令会清空数据。正常启动不得自动删除卷、重置活动额度或覆盖订单。开发者可复制仓库后按文档完成演示，不需要原工作区路径、私有资源或人工改源码。
