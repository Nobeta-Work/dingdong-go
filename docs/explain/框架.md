## 1. 当前项目是什么形态

项目是一个限量活动商城后端，采用一个 Go module、四个独立业务进程、各自拥有业务数据的结构。M1 建立登录、活动、受理、库存、订单和支付/关闭业务主线；当前 M2 又补齐详情缓存、限流、Lua 预扣与代次重建、Inbox、统一持久化队列、有界重试和验收工具。

“代码具备业务链路”与“已完成运行验收”要分开理解：当前 README 明确记载运行验收未执行。本次核对代码并更新讲解，不启动 Docker、不执行交易、不修改业务数据。

```text
运营创建/发布活动 ──RPC──→ 查询 SKU 和当前可用库存
用户提交抢购 → 原请求重放 → 限流 → Lua 活动预扣
                    ↓ SQL 最终事务
                 受理 + 资格 + 额度 + Outbox + 兜底任务
                    ↓ 提交后返回 202
Outbox ──RocketMQ──→ Inbox ──→ 操作任务 ──RPC──→ 预占库存
                    ↓ 本地事务生成订单
用户申请支付单 ──交易校验──RPC──→ 支付服务创建/获取支付单
用户模拟支付 ──事务──→ SUCCESS + PaymentSucceeded Outbox
                    ↓ RocketMQ
交易回查支付事实 → PAID + 库存确认事件 ──RPC──→ CONFIRMED

到期提醒/扫描 → CLOSING → 支付回查/关闭
                        ├─ SUCCESS：转 PAID，确认库存
                        └─ CLOSED：转 CANCELED，释放库存
```

### 2.1 cmd 是启动类吗

可以把 `cmd/<名称>/main.go` 类比为启动入口。Go 没有类；它是 `package main` 下的 `main()` 函数。cmd 是目录约定，不是语言要求，也不是本项目的一个 Go 包。四个业务入口只调用内部包的 Run，启动失败时记录日志并退出。

seed、diagnose 也有自己的 main，但它们是工具，不是长期运行的业务服务。一个程序的小项目可以直接把 main.go 放在根目录；本项目有多个程序，使用 cmd 很自然。

### 2.2 internal 不是一个“业务大包”

Go 对 internal 目录实施导入范围限制。项目在其中按领域划分 user、catalog、trade、payment，把公共技术能力放到 platform。

包由目录决定：`internal/trade` 中多个文件都属于 `package trade`，共享未导出的 service、createOrder 等标识符。拆文件为了阅读，不意味着文件之间是独立层或独立服务。

### 2.3 当前为什么没有 handler/service/repository 三层目录

当前按领域组织、包内按职责拆文件。例如 trade/order.go 组织订单业务及所属库 SQL，catalog/inventory.go 把库存事务放在同处，便于看清事务边界。并不要求先建立固定数量的目录或接口。

复杂度增加后，可以提取被 HTTP、RPC、消费者复用的业务层，再按需要提取 Repository。目的是复用规则、隔离变化。当前部分业务直接使用 gRPC status 表达错误，是简化取舍；若要进一步隔离领域与通信协议，可用领域错误，再分别转换成 HTTP/gRPC 错误。

### 2.4 platform 仍不决定商城规则

platform 提供配置、连接、鉴权协议和事件传输等能力；trade 决定支付成功后如何推进订单。event.Bus 会投递消息，但不会解释 PaymentSucceeded 的业务含义，后者由 trade.handleEvent 完成。

platform/app 当前仍含 TradeClients、CatalogConn 等项目拓扑字段，属于本项目公共运行层，不是完全通用的外部框架。是否优雅应看依赖边界与实际维护成本，不能只看目录名。

## 3. 四个服务与数据边界

| 服务 | 业务数据/能力 | 入站 | 出站 |
| --- | --- | --- | --- |
| user | 账号、角色、密码校验、JWT | HTTP | 所属库 |
| catalog | SKU、库存、预占流水 | HTTP、Catalog/Inventory RPC | 所属库 |
| trade | 活动、资格、受理、订单、补偿任务 | HTTP、MQ→Inbox | 所属库、Redis 缓存/限流/预扣、商品/支付 RPC、MQ |
| payment | 模拟支付事实、关闭标记、支付事件 | HTTP、Payment RPC | 所属库、MQ 生产 |

四个逻辑库共享一个 MySQL 实例，应用账号只具备所属库 DML 权限。服务之间不跨库 JOIN，不用一个 sql.Tx 包住远端 RPC 写入。diagnose 是专用只读工具，分别连接 trade/catalog/payment 并在内存比较，不提供跨服务全局读快照。

Go 模块路径是 `github.com/Nobeta-Work/dingdong-go`，与本地文件夹位置 `src/nobeta.cn/dingdong-go` 是不同概念。

## 5. M1 关键变化：Configure 与 Runtime

最初业务包只有一层 Run，资源封闭在 app.Run 内；现在通过回调装配业务。交易服务的启动声明包含：

```go
return app.Run(app.Spec{
    Name: "trade-service", Redis: true, MQ: true,
    TradeClients: true, Configure: configure,
})
```

Spec 的关键字段是 `Configure func(*Runtime) (func(context.Context) error, error)`。Runtime 提供 Config、DB、Router、RPC、CatalogConn、PaymentConn、Logger、Redis、Metrics 和 Faults。

`Configure: configure` 传入函数本身，不是提前执行。app 创建资源后调用它，业务包在其中注册 HTTP/RPC、构造业务对象并启动后台任务。

返回值可以拆开理解：外层 error 表示装配是否成功；返回的函数用于退出时清理业务资源，其 ctx 限制清理时间。user/catalog 返回 nil 清理动作，payment 返回 bus.Close，trade 返回同时关闭 Bus 与恢复扫描的闭包。

依赖方向仍是领域包导入 platform。platform 只按函数签名调用回调，不导入 catalog/trade，因此避免循环依赖。

### 5.1 启动顺序

```text
main → 领域包 Run → app.Run
  1. Load 配置：DSN、JWT_SECRET、PAYMENT_WINDOW、地址
  2. 创建日志、退出信号 ctx、所属库连接池
  3. 按 Spec 创建 Redis、长期复用的 gRPC 通道
  4. 并行检查依赖
  5. 创建 Gin router 与带错误映射 interceptor 的 gRPC server
  6. Configure 注册业务 HTTP/RPC，并启动 Bus/恢复任务
  7. 注册健康接口，启动 HTTP；按开关启动 gRPC
  8. 等待退出信号或监听异常
```

业务注册在 Serve 前完成。event.Start 会启动真实 MQ SDK，不只是 TCP 探测，因此 MQ 地址或连接故障也可能使 Configure 失败。

DB 是可复用连接池：最大连接 20、最大空闲 5、最长生命周期 5 分钟。驱动使用 UTC，禁用多语句，并显式关闭 ClientFoundRows；库存事务依赖 RowsAffected 区分首次插入和同键重放。

### 5.2 退出与清理

先撤销 HTTP/gRPC 就绪状态，再停止后台领取并排空 HTTP/gRPC，共享 15 秒预算；Compose 宽限 20 秒。之后释放连接池和客户端通道。若 Configure 成功但后续监听失败，defer 仍会调用业务清理函数。

退出函数并不单独保证业务恢复：持久化状态、稳定业务键、重投和幂等共同支撑收敛。真实退出和重启验收仍需运行检查。

## 6. HTTP、身份与错误

HTTP 先生成 traceId、设置 X-Trace-ID，并记录路径、状态、耗时。受保护路由再执行 auth.Require。用户登录时从所属库读取密码哈希，bcrypt 比对后签发两小时 HS256 JWT。

各服务验证算法、issuer=dingdong、有效期、正整数 subject 和角色，把可信 userId/role 放入 Gin context。运营接口要求 OPERATOR；访问订单/支付单还要核对资源归属。客户端 userId 不决定身份。

HTTP Handler 负责绑定、取身份、调用业务、输出协议。商品 HTTP 查询直接调用同进程 s.GetSKU，不会绕到网络再调用本服务。

httpx.Error 将 InvalidArgument→400、Unauthenticated→401、PermissionDenied→403、NotFound→404、AlreadyExists/FailedPrecondition/Aborted→409；SQL 1062 也转 409，ResourceExhausted 在 HTTP 入口映射为 429 RATE_LIMITED，其余依赖或未知错误通常转 503。HTTP panic 恢复返回 500。新受理提交成功返回 202，同参数重放返回 200。

共享 JWT 密钥只是 HTTP 身份方案，不代表内部 gRPC 已鉴权；当前 RPC 仍为明文且未实现独立身份校验。

## 7. 真实 RPC 装配

商品 configure 创建实现对象并注册：

```go
s := &catalogService{db: r.DB}
pb.RegisterCatalogServer(r.RPC, s)
pb.RegisterInventoryServer(r.RPC, &inventoryService{db: r.DB})
```

支付 configure 注册 RegisterPaymentServer。业务服务和标准 Health 共用各自实际执行 Serve 的同一个 gRPC server。

trade/models.go 创建 CatalogClient、InventoryClient、PaymentClient。前两个共享 CatalogConn，支付使用 PaymentConn；app 管理通道关闭，业务请求只借用代理。

rpcContext(parent) 给每次同步调用一秒预算。写入结果未知时按同一业务键回查。app 的一元 interceptor 记录失败，保留已有 status，将 sql.ErrNoRows 转 NotFound、上下文错误转相应状态，其他底层错误转 Unavailable。

M2 已将 HTTP/任务 ctx 的 traceId 通过客户端 interceptor 写入 x-trace-id metadata，并在服务端失败日志读取；还记录 RPC 次数、耗时、失败和超时。当前没有通用 RPC panic 恢复、TLS 或内部鉴权。Health 的 SERVING 表示 RPC 启动状态，不替代各服务 /readyz 的依赖检查。

## 8. 数据事实与运行机制

| 事实 | 所属表 | 作用 |
| --- | --- | --- |
| 用户 | user.users | 用户名唯一、角色约束、密码哈希 |
| SKU/库存 | catalog.sku、inventory | 商品启用、价格、库存非负与守恒 |
| 预占 | catalog.inventory_reservation | order_no+sku_id 唯一，预占/确认/释放 |
| 活动额度 | trade.activity.used_quota | 事务内计数且 0≤used_quota≤quota |
| 参与资格 | trade.activity_participation | activity_id+user_id 主键，资格状态 |
| 受理 | trade.activity_request | 请求幂等、参数哈希、快照、稳定订单号 |
| 订单 | trade.orders、order_items | 同用户同活动最多一单、价格与商品快照 |
| 支付 | payment.payment | 订单唯一，成功与关闭互斥 |
| 事件 | trade/payment 各自 outbox | 持久化排期、租约、发送状态和重试记录 |
| 入站事件 | trade.event_inbox | 原始消息持久化、eventId 去重、deliveries、可靠转交任务 |
| 操作任务 | trade.operation_task | 成单/关闭/库存、缓存失效、准入确认/回补/重建 |
| 准入栅栏 | trade.activity 的 epoch/state/revision | Redis 恢复时阻挡旧许可，检查分页快照 |

M2 已把 Outbox/Inbox/operation_task 接入统一 Queue，提供十五秒租约、每次领取 token、有界退避、NEEDS_REVIEW 和运营 retry。机制与验收工具已实现；运行是否达到预期仍需真实验收。

## 9. 部署与 Bash 操作入口

下面命令供后续手动执行，本次未运行。先确保 Docker Linux 引擎可用；首次复制配置，已有 .env 不覆盖：

```bash
if [ ! -e .env ]; then
  cp .env.example .env
fi
# 先编辑 .env，确认密码、JWT_SECRET 和支付窗口。
docker compose config --quiet
docker compose up -d --build
docker compose ps -a
docker compose run --rm seed-user
docker compose run --rm seed-catalog
```

JWT_SECRET 至少 32 字节且四服务一致；PAYMENT_WINDOW 默认 120s，允许 5s～1h。配置变化不会修改已落库订单的 expiresAt。种子用户 503 个，两个 SKU 各 200 件、1990 分，重复初始化不重置现有账号和库存。

| 服务 | 宿主机 HTTP | 宿主机 gRPC |
| --- | --- | --- |
| user | 18080 | 无 |
| catalog | 18081 | 19000 |
| trade | 18082 | 无 |
| payment | 18083 | 19001 |

容器内 HTTP 为 8080，商品/支付 RPC 为 9000，互相通过服务 DNS 调用。scratch 镜像没有 shell，所以健康检查使用编译后的 healthcheck。cmd/verify 没有打进该镜像，acceptance.sh 在使用者的 Go 环境执行 go run ./cmd/verify，作为外部 HTTP 验收客户端。

```bash
for port in 18080 18081 18082 18083; do
  curl --fail --silent --show-error "http://localhost:$port/livez"
  curl --fail --silent --show-error "http://localhost:$port/readyz"
done
docker compose run --rm mqcheck
# 业务静止、状态收敛后执行独立只读诊断。
docker compose run --rm diagnose
```

### 9.1 IDE 调试时 Broker 地址为何更重要

## 11. 当前进程里到底启动了哪些后台组件

交易 configure 位于 [trade/http.go](../../internal/trade/http.go)，按下面顺序读最直观：

```text
newService(Runtime)
  → newActivityCache：服务级共享加载 ctx、singleflight、预算 channel
  → work.New(operation_task, handleTask)：本地业务动作队列
  → routes：公开详情、用户接口、运营接口
  → event.Start：Outbox 发送队列 + MQ 入库 + Inbox 转任务
  → jobs.Start：业务任务工作者
  → recoverLoop：定期补齐 SQL 任务、检查 Redis 准入状态
```

依赖不是所有组件互相乱调：cache 只服务展示读取；rate 只决定流量是否通过；admission 管理临时额度与数据库许可；jobs 执行真实业务方法；Bus 管消息传递。共同依赖的 DB 始终是本服务所属库。

默认一个 trade 实例有一个 Outbox 工作协程、八个 Inbox 工作协程、八个 operation_task 工作者，外加恢复扫描及 SDK 内部协程。WORKER_CONCURRENCY 控制本地固定工作数，不代表整个进程只有八个 goroutine；两个实例各有自己的工作协程，共用数据库协调领取。

payment 只需要 Outbox，无交易 Inbox 和操作任务；catalog 不消费这些业务事件，接受 gRPC 库存操作。

## 12. 学习 Go 时重点留意的实现方式

| 写法 | 项目位置 | 为什么这样用 |
| --- | --- | --- |
| 函数类型 Configure | platform/app、各 service.go | 框架提供资源，领域包注入装配动作，避免循环导入 |
| 闭包清理函数 | trade.configure | 捕获 cache、Bus、Queue、cancel，统一按退出预算清理 |
| 按值匿名嵌入生成默认服务 | catalog/payment | 满足 gRPC 服务接口并保留新增方法的默认兼容 |
| chan struct{} 作为预算 | trade/cache.go | 只表达占位，不存业务数据，限制不同 key 回源并发 |
| singleflight.DoChan | trade/cache.go | 同 key 共享加载，等待者可独立取消 |
| go:embed lua/*.lua | trade/admission.go | 将脚本编进二进制，运行镜像不依赖外部脚本路径 |
| SQL Tx + defer Rollback | 各业务事务 | 任一路径提前返回都可清理；Commit 成功后 Rollback 不再产生业务回滚 |
| QueryRowContext/ExecContext | 业务与队列 | 将预算和取消传入数据库，不代表已提交结果会被撤销 |
| RowsAffected + 条件 WHERE | 库存/任务 | 区分首次动作、重放及旧 token，不能只判断 err==nil |
