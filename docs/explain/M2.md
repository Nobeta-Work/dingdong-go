# M2 原理与实现：缓存、准入恢复和持久化工作队列

更新于 2026-10-26，依据当前源码核对。本文先解释为什么需要这些机制、各机制防哪一种错误，再给出已有验收工具的操作说明。所有命令为 Bash；本次没有运行服务、Redis/Lua、数据库、MQ 或故障验收。

先读 [M1 业务流程](M1业务流程.md) 掌握业务状态，再读本篇。完整源码阅读入口见 [README](README.md)，目录装配见 [框架](框架.md)，接口路径见 [API](../../API.md)。

## 1. M2 改变了什么，什么仍然不变

M1 要解决“能不能完成一笔正确购买”；M2 在相同业务规则上处理热点、并发、重投、进程退出以及 Redis 数据丢失后的恢复。M2 不是简单把 MySQL 的计数搬到 Redis。

仍然不变的规则包括：同用户同活动最多一张订单；订单取消不恢复活动资格；真实 SKU 库存由 catalog 拥有；支付事实由 payment 拥有；只有 PAID+CONFIRMED 可履约；远程写超时不能直接判定失败。

当前提交路径：

```text
HTTP 鉴权/参数检查
  → SQL 原请求重放
  → 用户令牌桶 → 活动令牌桶
  → Redis Lua 预扣活动额度和资格，生成 ticket
  → SQL 最终确认：活动锁 + 代次/版本/时间/额度/资格
  → 请求、资格、used_quota、Outbox 与任务同事务提交
  → HTTP 202
```

当前异步路径：

```text
发送库 Outbox → RocketMQ → 接收库 Inbox → operation_task → 领域业务方法
                                  ↑                       ↑
                     SDK 先保存原消息再确认 MQ      SQL 提交时兜底任务 / 恢复扫描补齐
```

理解本篇时始终区分：读取加速、流量保护、临时预扣、持久化受理、真实 SKU 预占、支付事实、工作调度。这些层各有自己的数据和成功条件。

## 2. 用三个数量理解“限量”

假设 SKU 总库存 200，活动 A 的 quota=10，SQL 已持久化 used_quota=3，Redis 还有两条未确认预扣。

| 数量 | 此时的含义 |
| --- | --- |
| catalog.inventory.available | SKU 全局剩余量，可能还受其他活动订单影响 |
| activity.quota-used_quota = 7 | 数据库事实中，活动尚未正式消耗的额度 |
| Redis remaining 可能为 5 | 镜像基于剩余 7 又临时扣住两条 ticket |

Redis 多扣住的两份不是库存丢了，而是“预扣→持久化受理”之间的窗口。成功落库后确认 ticket；确认未落库失败后再回补。Redis 重建从 SQL 剩余 7 和已持有资格重建，旧 ticket 必须被代次挡住，不能继续按旧许可写入。

因此 Redis remaining 与 quota-used_quota 不要求每时每刻相等。诊断时必须结合 pending、SQL 请求和代次，不能看到一瞬间差异就直接重置为满额。

## 3. 活动详情缓存：保护读，不授权交易

源码：[cache.go](../../internal/trade/cache.go)、[activity.go](../../internal/trade/activity.go)。

### 3.1 Cache-Aside 的实际过程

公共 `GET /api/activities/:id` 使用详情缓存；活动列表仍查询 SQL，并非所有查询都缓存。

```text
GET Redis detailKey
  ├─ 命中 JSON：解码后重新计算 phase，返回
  ├─ 命中 null：返回不存在
  └─ 未命中/错误/坏 JSON
       → 本实例 singleflight.DoChan(id)
       → 再查一次 Redis
       → 尝试取得本实例回源预算
       → 查 SQL，只公开 PUBLISHED/PAUSED
       → 写 JSON 随机 TTL，或 null 短 TTL
```

缓存键是 `dingdong:activity-detail:<id>`。正常 TTL 随机选 60～75 秒，空值 TTL 为五秒；它们和准入 ticket 是不同键、不同生命周期。

正常 TTL 抖动减少大量活动同时到期，空值缓存减少不存在活动反复打数据库。未公开草稿也按公开不可见结果缓存 null，不缓存数据库技术错误为不存在。

### 3.2 singleflight 与预算各防什么

同一实例一百个请求同时查询活动 A，singleflight 让同 key 共享一次加载；进入共享函数后再查 Redis，是为了吸收其他实例或刚结束加载填入的结果。

但一百个不同活动是不同 key，singleflight 不会合并，所以还需要容量为 CACHE_ORIGIN_LIMIT 的 channel，默认每实例 16。满时立即返回 503，不无限等待或无限起 SQL 查询。

两个 trade 实例各有自己的 singleflight 和预算，不是跨进程分布式锁。共享 Redis、双重检查可减少重复，但一个冷 key 在两个实例各回源一次仍可能发生。双实例缓存验收因此检查 1～2 次回源增量，不声称全局一定一次。

### 3.3 context 为什么分成两层

单个 HTTP 等待者使用自己的 ctx 选择退出；共享加载使用 cache 的服务级 ctx，再设置两秒预算。这样一个客户端断开，不会把另一个仍在等待的客户端共享加载取消。服务关闭时 cancel cache 的 ctx，才整体停止共享加载。

单次 Redis 读写另设 300ms。Redis 查询失败在此读场景可尝试 SQL，但仍受回源预算；写缓存失败记录指标，查询事实本身仍可返回。这与抢购新准入 Redis 失败必须拒绝，是两种不同降级策略。

### 3.4 缓存失效与实际一致性边界

更新标题、暂停、发布激活相关事务保存 InvalidateActivityCache 任务；标题/暂停提交后也尝试立即 DEL。若立即失效失败，任务继续重试，超过阈值保留 NEEDS_REVIEW。

这是最终一致的展示缓存，不是严格线性一致。数据库回源与更新/DEL 并发时，仍可能短暂写回旧展示值；TTL 是兜底之一。准入和支付校验不读取详情缓存，因此陈旧展示不能直接变成交易授权。

缓存中的 phase 每次返回前按当前时间计算，避免缓存了六十秒还一直显示旧的 UPCOMING；发布状态和标题仍遵循失效与 TTL 规则。

## 4. 两层令牌桶：限速不等于卖完

源码：[rate.go](../../internal/trade/rate.go)、[rate.lua](../../internal/trade/lua/rate.lua)、[errors.go](../../internal/platform/httpx/errors.go)。

### 4.1 令牌桶怎样理解

burst 是桶能存多少令牌，rate 是每秒补多少。每次新请求消耗一枚，不足就拒绝。补充公式为：

```text
tokens = min(capacity, oldTokens + max(0, now-oldTime) × rate)
tokens >= 1：减一并允许；否则拒绝
```

Lua 用 Redis TIME 作为共享时间，时间单位换算为毫秒；令牌可以是小数。不存在的桶从满桶开始，TTL 设置得比补满周期更长，所以久未访问重新建满不额外突破该模型。

默认用户桶 3/1：最多存三枚，每秒补一枚；不是固定“每自然秒恰好三次”。活动桶 500/100：吸收活动级突发。默认值可配置，多实例必须一致。

### 4.2 真实执行顺序

requestLimit 中间件先解析 requestId、归一化 activityId、查询 SQL 重放。找到原结果就返回 200；参数不一致返回 409，不消耗新令牌。

未持久化结果才依次执行用户桶、活动桶。两个桶各自原子，但两桶之间不是一个事务；活动桶拒绝不会退用户桶令牌。限流拒绝后还会再查一次 SQL，吸收同键并发刚提交的结果，避免错误地把成功重放当 429。

限流通过后将 requestId 放进 Gin context，handler 再调用 submit。submit 本身也检查 SQL 重放，防止中间件检查后另一并发请求刚提交。

### 4.3 返回码表示不同事实

| 结果 | 含义 | 是否可以当“库存卖完” |
| --- | --- | --- |
| 429 USER_RATE_LIMITED | 用户流量桶不足 | 不可以 |
| 429 ACTIVITY_RATE_LIMITED | 活动流量桶不足 | 不可以 |
| 409 ACTIVITY_QUOTA_EXHAUSTED | 活动准入额度不够 | 是活动额度限制，不是 SKU 全局库存数 |
| 503 | 依赖/准入元数据不可用或重建中 | 不可以，不能伪装业务失败 |
| 202 | SQL 受理已提交 | 不保证成功成单 |
| 请求最终 FAILED，原因 SKU_STOCK_UNAVAILABLE | 异步库存预占明确拒绝 | 是该次真实库存动作的结果 |

catalog 的 ResourceExhausted 在 createOrder 中被识别成业务失败，通常不是原样透传成抢购 HTTP 429。不能只看同一个 gRPC 枚举，就忽略它在哪条入口被消费。

## 5. Redis 预扣的四个键

源码：[admission.go](../../internal/trade/admission.go)、[admit.lua](../../internal/trade/lua/admit.lua)。

同活动键格式：`dingdong:{activity:<id>}:config/holders/records/pending`。

| 键 | Redis 类型 | 保存内容 |
| --- | --- | --- |
| config | Hash | epoch、ready、remaining、quota、status、version、starts/ends、builder |
| holders | Hash | userId → userId:requestId，以及 __epoch__ 哨兵 |
| records | Hash | userId:requestId → ticket JSON，以及 __epoch__ 哨兵 |
| pending | Sorted Set | 未确认 ticket 的创建毫秒时间索引，以及 score=0 的哨兵 |

`{activity:<id>}` 是 Redis Cluster hash tag，让同一活动四键落入同一 slot，Lua 可一起处理。它不是 Go 占位语法。当前本地部署是单 Redis，键设计兼顾同槽约束并不等于已验收 Redis Cluster。

ticket 保存 activityId、userId、requestId、固定 orderNo、parameterHash、epoch、version、createdMs、state。业务 ID/epoch/version 用字符串，避免 Lua/JSON double 精度破坏大整数。

### 5.1 admit.lua 的检查和写入顺序

```text
检查 config 存在、ready=1，三个辅助键哨兵完整且代次匹配
  → 检查活动 PUBLISHED、Redis 时间在活动区间内
  → 查同用户同 requestId 记录：同 hash 返回原 ticket，不重新扣
  → 查用户是否已持有资格
  → 查 remaining > 0
  → remaining-1
  → 写 holders、records、pending
  → 返回 OK + ticket
```

这些命令在一次脚本执行中完成，不存在先 GET 再 DECR 的客户端间隙。Lua 的原子范围仅是这些 Redis 操作，不包含之后的 MySQL 事务或 SKU 库。

ticket 的 PREHELD 只表示活动临时预扣，没有返回 202，也没有预占 SKU。config/索引缺失时返回 REBUILD，Go 调度 SQL 重建并向当前请求返回 503，不能无条件放行。

### 5.2 为什么不给 ticket 一个自动过期 TTL

如果五秒后 ticket 自动消失，但请求实际已提交 SQL、只是响应丢失或确认慢，自动增加额度会再次放出已经消耗的资格。当前实现保留记录，由 pending 索引发现异常，再按 SQL 事实确认或回补。

五秒是扫描候选年龄，不是 ticket 生命周期；pending.lua 排除 score=0 哨兵，每次最多取一百条。重建也只重建数据库可证明的持有事实，不把 Redis 丢失当作业务记录删除。

### 5.3 Go 如何把参数交给 Lua

prehold 的真实调用片段是：

```go
result, err := admitScript.Run(ctx, s.redis, admissionKeys(id), string(body)).StringSlice()
```

`admissionKeys(id)` 的四个元素依次变成 Lua 的 KEYS[1]～KEYS[4]；string(body) 是 ARGV[1]。Lua 下标从一开始，与 Go slice 的零下标不同。脚本的返回 `{'OK', payload}` 对应 Go 的两元素字符串切片。

Redis 命令或脚本执行错误走 err；`QUOTA/HELD/CONFLICT/REBUILD` 是脚本成功执行后的业务分支，Go switch 再转换为 409 或 503。不能把“没有 err”理解为已经拿到预扣。

admission.go 用 go:embed 将 lua/*.lua 编入二进制，再按名字构造 redis.Script。运行时不要求工作目录里额外存在 Lua 文件；修改脚本仍需要重新构建应用。

### 5.4 七个脚本各负责哪个边界

| 脚本 | 调用阶段 | 主要输入/保护条件 |
| --- | --- | --- |
| [rate.lua](../../internal/trade/lua/rate.lua) | 两类令牌桶 | 一个桶键、capacity、rate，Redis TIME |
| [admit.lua](../../internal/trade/lua/admit.lua) | 新 ticket 预扣 | 四个同槽键、ticket JSON、完整 ready/epoch/资格/额度 |
| [pending.lua](../../internal/trade/lua/pending.lua) | 发现未确认预扣 | 同四键，查询 score≥1 且年龄超五秒的前一百条 |
| [resolve.lua](../../internal/trade/lua/resolve.lua) | ACK 或 REFUND | user、requestId、动作；当前 holder 核对 |
| [prepare.lua](../../internal/trade/lua/prepare.lua) | 重建初始化 | epoch、builder、SQL 剩余额度和活动配置 |
| [rebuild.lua](../../internal/trade/lua/rebuild.lua) | 分页填充 | epoch、builder、每页 DURABLE ticket |
| [activate.lua](../../internal/trade/lua/activate.lua) | 最后开门 | epoch、builder 匹配后 ready=1 |

holders 和 pending 的运营计数包含一个 `__epoch__` 哨兵：holderEntries=1 可能表示没有用户持有，pendingEntries=1 表示没有待确认 ticket；不能把这个一当成一位用户。pending 的哨兵 score=0，脚本从 score=1 起取，避免当普通 ticket 处理。

## 6. SQL persistTicket：临时许可必须再过最终校验

源码：[request.go](../../internal/trade/request.go)。

SQL 开 READ COMMITTED 事务，锁活动行，然后查 userId+requestId 原结果。只有新请求才核对以下条件：

1. admission_state=ACTIVE，ticket.epoch 等于数据库 epoch。
2. ticket.version 等于活动 version。
3. 发布状态、开始/结束时间仍允许新受理。
4. used_quota < quota。
5. 活动用户资格仍为 AVAILABLE。

成功事务同时写：ACCEPTED 请求与快照、HELD 资格、used_quota+1 和 admission_revision+1、CreateOrderRequested Outbox、十秒后成单兜底任务、AcknowledgeAdmission 确认任务。事务成功后才返回 202。

明确拒绝时先持久化 FAILED 和 failureReason，同事务写 RefundAdmission，再提交返回冲突；SQL 技术错误或提交结果未知不能直接当 FAILED。

这里保留活动行锁与 SQL 约束，说明 M2 并没有消灭数据库最终争用。Redis 过滤流量与临时占位，SQL 仍是持久化裁决者，不能据此推导无限扩展的吞吐结论。

## 7. 预扣后未落库：先写失败，再退款

源码：admission.go 的 terminalizeHold、worker.go 的 scanAdmission/handleTask、lua/resolve.lua。

设用户 U 的 R1 已在 Redis 扣一份，但进程在 SQL 提交前退出。过了候选年龄，扫描拿到 ticket 后先锁 SQL 活动行，再查 U+R1：

```text
SQL 已有 ACCEPTED/PROCESSING/ORDER_CREATED → 写确认任务，不回补
SQL 已有 FAILED                         → 写回补任务
SQL 没有这次请求                        → 插入 FAILED(ADMISSION_NOT_PERSISTED)
                                          与回补任务同事务提交
```

### 7.1 为什么一定要先落 FAILED

若先给 Redis 返还额度，原请求的 SQL 事务却随后成功提交，就会出现“一份返还给别人，旧请求仍受理”的窗口。

先写失败终态与迟到 persistTicket 竞争同一活动锁和请求唯一键：谁先提交决定事实；迟到请求只能读取这个原结果，不能再次建单。若 SQL 不可写，宁可继续保留预扣、暂停该结果的释放，也不能猜测失败。

### 7.2 ACK 与 REFUND 的区别

ACK 把 ticket 标记 DURABLE 并移除 pending，不返还 remaining，不删除用户资格。它证明 SQL 已存在，并不表示订单已支付。

REFUND 只有在 SQL 事实允许时执行；Lua 核对 holders[user] 仍为同一 user:requestId 才删除持有并返还一次，remaining 不超过 quota，再删除对应记录和 pending。重复执行不会重复加一，也不会释放用户后来获得的新 requestId。

回补不强制旧 ticket epoch 等于当前 Redis epoch：新代次重建可能已复制了该请求的持有事实，匹配当前持有者后仍应能安全清理。安全条件是 SQL 已有相应终态和 holder 对应，不是盲目给任意代次加一。

成单前最终失败还会减少 SQL used_quota、释放 HELD、增加 revision 并投递库存释放动作；预扣压根没落 ACCEPTED 的失败则不应去减未曾加过的 used_quota。

## 8. Redis 丢失后的重建：四个标识各管一件事

| 标识 | 位置 | 保护什么 |
| --- | --- | --- |
| admission_epoch | SQL + Redis + ticket | 区分重建代次，拒绝旧许可落库 |
| admission_revision | SQL 活动行 | 发现分页快照期间持有/额度/暂停等事实变化 |
| builder token | Redis config | 防旧重建者继续写进另一重建者的数据 |
| work.Item.Token | SQL 工作队列 | 防旧领取者覆盖新一次领取的完成状态 |

这四者不能互相替代，尤其不能把 builder 和工作租约令牌当作同一个锁。

### 8.1 COLD、RECOVERING、ACTIVE 与 ready

SQL admission_state 有三个值：COLD 尚未初始化，RECOVERING 正在重建，ACTIVE 已完成数据库侧激活；Redis ready=1 表示该代次镜像可以接受预扣。

活动 status=PUBLISHED 是业务发布状态，admission_state=ACTIVE 是准入镜像状态，详情 phase=ACTIVE 又是时间阶段，三个 ACTIVE 的语境必须分开。

新预扣发现缺键/哨兵不完整，或扫描发现元数据不完整时，scheduleRebuild 锁活动行；不在 RECOVERING 则 epoch+1 并转 RECOVERING，保存 RebuildAdmission 任务。已经处于同代次恢复时复用，不每次请求无意义增加 epoch。

### 8.2 分页重建的实际步骤

```text
SQL 提交新 epoch + RECOVERING + 重建任务
  → 读取并短暂锁定本代次活动快照，释放事务
  → prepare.lua：ready=0，设置 builder，remaining=quota-used_quota
  → 每页最多 100 个 HELD/CONSUMED 资格及对应请求
  → 读完关闭 rows，再 rebuild.lua 检查 epoch/builder 并写入
  → SQL 再锁活动，核对 epoch、RECOVERING 和 revision 未变
  → SQL 提交 ACTIVE，必要时 PUBLISHING→PUBLISHED，写缓存失效任务
  → activate.lua 检查 epoch/builder，ready=1
```

重建不持有 SQL 长事务做 Redis 网络请求，也不把全部用户资格累积到内存。prepare 的 builder 有十五秒领取保护；后续页写入必须仍匹配该 builder。代次比较使用规范十进制字符串长度和字典序，避免 Lua double 比较 BIGINT。

若是从 PUBLISHING 恢复，buildAdmission 还会 RPC 检查 SKU 启用和额度，不能绕过正常发布校验。

### 8.3 用旧请求解释 epoch 栅栏

```text
R1 在 Redis epoch=7 得到 ticket，尚未 SQL 提交
Redis 丢失
SQL 先切 epoch=8、RECOVERING
R1 恢复，持 ticket(epoch=7) 调 persistTicket
SQL 读 epoch=8 → 拒绝旧 ticket，持久化失败与回补安排
新代次镜像完成后才允许新请求预扣
```

若只重建 Redis 而不先修改数据库 epoch，R1 可能在新额度放出后继续落库；旧许可不失效，恢复反而制造重复销售窗口。

### 8.4 revision 与 builder 的分别作用

分页读取时，旧受理可能最终失败，改变 HELD 资格和 used_quota，或运营暂停活动。revision 改变意味着快照前提变了，最终 SQL 检查失败，不能激活混合快照，需要重试。

重建工作者 A 卡住，B 接管了 Redis 重建；A 恢复时即使还拿着同 epoch，也必须因 builder 不匹配而停止写页。epoch 保护业务许可，builder 保护同代次重建的执行者。

### 8.5 SQL ACTIVE 后 Redis 激活失败怎么办

这两个系统没有共享事务。SQL ACTIVE 与 Redis ready=1 之间可以失败；此时新预扣仍被 ready 拒绝，后续检测推进新的 SQL 代次重新构建。实现选择牺牲短暂可用性，避免在半初始化镜像上继续准入。

恢复使用 quota-used_quota，并复制 HELD/CONSUMED，不重新给满额，不恢复已取消订单的资格。现有 M1 数据迁移后默认 COLD，可据数据库事实初始化。

## 9. Outbox、Inbox、任务：三层都为什么要有

源码：[event/bus.go](../../internal/platform/event/bus.go)、[worker.go](../../internal/trade/worker.go)。

| 层 | 保存的事实 | 该层完成意味着 |
| --- | --- | --- |
| Outbox | 待发送 Envelope | Broker 已确认发送，状态 SENT |
| event_inbox | 原始入站消息 | 已验证/转交为本地任务，状态 DONE |
| operation_task | 业务键+动作+payload | 当前业务方法处理成功，状态 DONE |

Outbox 解决“数据库提交了，但消息未发”；Inbox 解决“先 ACK，进程再退出，收到的消息消失”；任务队列解决“收到事件后如何有界重试、与本地恢复路径合并”。

### 9.1 发送与确认窗口

event.Put 与业务同事务，eventId 由事件类型+aggregateId 确定，重复 Put 不改已发送状态。Outbox 工作者 SendSync 成功后由通用队列标 SENT。

Broker 已收到、标 SENT 前退出时，会再发相同 eventId。事件 ID 只是去重标识，不提供分布式 exactly-once。支付成功、订单终态等仍必须靠本地唯一键和终态检查处理重复。

### 9.2 三处 payload 不是同一个层级

读 SQL 和 JSON 时容易混淆名称：

| 位置 | payload 实际内容 |
| --- | --- |
| Envelope.Payload | 业务负载，例如 orderNo |
| outbox.payload | 整个 Envelope 的 JSON，含 eventId、eventType、traceId 以及内部 payload |
| event_inbox.payload | 从 MQ 收到的原始消息体，通常就是整个 Envelope JSON，也可为待排查坏消息 |
| operation_task.payload | 某动作需要的参数，例如 orderNo 或 activityId/userId/requestId |

例如业务先构造 `{orderNo: ...}`，event.Put 再把它包装进信封并保存；Inbox worker 解信封后，handleEvent 按 eventType/aggregateId 建立业务任务。并不是把同一个 JSON 原样在每张表里解释成相同 Go 类型。

这里 `eventId` 决定 Inbox 去重，`aggregateId` 在当前订单事件中通常是 orderNo；任务另用 business_key+action 去重。队列行自增 id 只用于定位/领取记录，不替代这些业务键。

### 9.3 SDK 消费回调现在只做可靠入库

回调把原始消息存入 event_inbox；同 eventId 再到只增加 deliveries，不重置 DONE/NEEDS_REVIEW。落库失败返回 ConsumeRetryLater；落库成功即可 ACK。

非法 JSON 或 eventId 不合法时，使用原消息字节生成稳定后备 ID，原始内容仍存 MEDIUMTEXT。之后 Inbox 处理失败、有界重试并保留人工检查状态，不因为解析不了就静默丢弃。

本地 RETRY_LIMIT 限制工作处理尝试；Broker 侧持久化失败重投是另一机制，不能理解为消息在二十次网络失败后就一定丢弃。

### 9.4 Inbox 怎样转成任务

Inbox worker 调 trade.handleEvent，校验事件版本、UUID、aggregateId 和已知类型，在 SQL 事务里 PutTask；本地转交成功后 Inbox 才标 DONE。它不直接执行长时间库存 RPC。

operation_task 唯一键为 business_key+action。重复 PutTask 只把 PENDING 的 next_attempt_at 提前，不清零 attempts，不改变 PROCESSING/DONE/NEEDS_REVIEW。

因此 Inbox DONE 不表示订单一定 ORDER_CREATED，task DONE 也不表示整张订单一定已履约：CreateOrderRequested DONE 只表示成单动作完成；后面还有支付和库存收尾。

## 10. 队列领取、退避和人工检查

源码：[work/queue.go](../../internal/platform/work/queue.go)、[work/http.go](../../internal/platform/work/http.go)。

### 10.1 同一套 Queue 用于三张固定表

Queue 只允许 outbox、event_inbox、operation_task，不从 URL 接受任意表名。Outbox 一个工作协程；Inbox 与任务各按 WORKER_CONCURRENCY 启动，默认各八个、范围一到八个。

```text
claim（两秒 ctx、短事务）
  → 选到期 PENDING 或租约过期 PROCESSING
  → FOR UPDATE SKIP LOCKED
  → 检查尝试次数，生成新 UUID token
  → attempts+1，PROCESSING，lease_until=现在+15秒
commit
  → handler（设置十秒处理预算，网络动作不持锁）
  → 独立两秒 ctx 写回（即使处理 ctx 已取消）
  → WHERE id=? AND status=PROCESSING AND lease_owner=本次token
```

每次领取都生成 token，不仅每个进程启动时生成 owner。完成更新若影响零行，说明该次结果已经过期，不能覆盖后来领取者。

### 10.2 旧执行者为何危险

A 领取 token=a 后卡顿，十五秒后 B 用 token=b 接管。A 恢复并返回成功；若只按 id 更新 DONE，会抹掉 B 的当前状态。附带 lease_owner=a 条件后，A 写不进去。

这个条件只保护队列完成记录，不撤销 A 已发出的 RPC；ctx 预算也是协作取消，不会强杀任意 Go 代码。因此业务仍要按稳定业务键幂等，不能因为有租约就删除库存/支付终态检查。

### 10.3 有限退避的实际数值

失败延时依次约 200ms、400ms、800ms、1.6s、3.2s，之后封顶五秒；没有宣称随机抖动。默认 RETRY_LIMIT=20，领取后进程退出、租约到期重新领取也累计 attempts。

达到阈值保留 NEEDS_REVIEW。Outbox 成功终态 SENT，Inbox/任务成功终态 DONE。重复消息或扫描不自动重置人工检查状态，否则会绕过重试上限持续冲击坏依赖。

### 10.4 运营恢复的顺序

先看 lastError、payload、业务键和相关服务事实；修复原因后，对具体 NEEDS_REVIEW 记录调用 retry。该操作改回 PENDING、attempts=0 并清理租约，不直接把订单改成成功。

普通 retry 不处理 DONE/SENT。演示开关开启时，SENT Outbox 另有 replay，用于真实重复投递实验；不能把 replay 当普通积压恢复。

## 11. 多条唤醒路径怎样合并而不重复执行业务

SQL 受理同时写 CreateOrderRequested Outbox 与十秒后兜底任务；消息正常到达，Inbox 转任务时将同键 PENDING 提前；消息延迟，本地兜底任务到时也能执行。

建单同时写 expiresAt 到期 Outbox 与 expiresAt+5秒任务；finishOrder 写库存收尾 Outbox 和五秒后任务。固定时间来自业务事实，不因重试修改订单 expiresAt。

recoverLoop 每五秒分页扫描：超十秒 ACCEPTED/PROCESSING 补成单任务；到期订单补 OrderExpiryDue；PAID/CANCELED 仍 LOCKED 补库存动作；活动元数据检查与预扣异常处理走 scanAdmission。

扫描现在只补任务，不在扫描循环中直接发库存/支付 RPC。队列负责并发、预算、租约与退避；同键 PutTask 去重和业务幂等保证多来源可以重叠。

如果任务已经 NEEDS_REVIEW，扫描不会救活它。扫描有触发间隔、分页和执行耗时，不能把“五秒扫描”解释成任何故障五秒内必恢复。

## 12. 观测、故障注入与读日志的方法

源码：[metrics](../../internal/platform/metrics/metrics.go)、[fault](../../internal/platform/fault/fault.go)、[app](../../internal/platform/app/app.go)。

HTTP 会生成 traceId 并写进 Go ctx；RPC 客户端 interceptor 转为 x-trace-id metadata，服务端失败日志读取该字段；任务的 trace_id 又由 handleTask 放回 ctx。事件、RPC 与业务日志已有基本关联，不再是旧版的“尚未传播 RPC traceId”。

当前指标属于进程内存：计数、耗时 count/sum_us/max_us。sum/count 可算平均，不能算分位数；重启清零，bootId 用于识别新进程，不是全系统持久化审计平台。

排查顺序建议：HTTP 响应 traceId/requestId → SQL 请求 orderNo → Outbox eventId → Inbox deliveries/status → operation_task action/lastError → 目标服务日志与库存/支付事实。

DEMO_FAULTS_ENABLED 默认 false。开启后仍需 OPERATOR，故障点只允许已注册位置，fail/delay/crash 是真实处理路径中的动作，不是返回伪造成功。规则只属于命中的实例，重启丢失，另一个 trade 实例不会自动共享。

## 13. 按失败位置选择恢复依据

| 失败窗口 | 不能直接做什么 | 当前恢复依据 |
| --- | --- | --- |
| Lua 预扣后、SQL 前退出 | 不能 TTL 到期就返还 | pending→SQL 失败/已有请求→ACK/REFUND |
| SQL 提交后 HTTP 响应丢失 | 不能换新 requestId 重卖 | 同用户同 requestId 重放 |
| Broker 收到、Outbox 未标 SENT | 不能假定没发过 | 同 eventId 重投，Inbox 去重 |
| Inbox 入库后进程退出 | 不能只依赖 SDK 再送 | 本地 Inbox 队列恢复 |
| 任务业务提交后、队列未 DONE | 不能再次产生新业务键 | 原键幂等重做 |
| Reserve 已提交、响应超时 | 不能当缺货 | GetReservation 与后续重试 |
| 支付已 SUCCESS、事件延迟 | 不能到期一律取消 | QueryByOrder/CloseByOrder 裁决 |
| Redis 全丢但旧请求仍在途 | 不能重建满额直接开门 | SQL 新 epoch、revision 校验、builder、ready |
| 重试次数耗尽 | 不能扫描时清零继续冲击 | NEEDS_REVIEW、运营显式 retry |

## 16. 故障矩阵与运行报告

| 场景（各五组） | 实际动作与主要检查 |
| --- | --- |
| 重复支付成功事件 | 重投 SENT 的原 Outbox，检查同 eventId 的 Inbox deliveries≥2，订单/售出数只增加一次 |
| 成功通知延迟 | 支付 before_outbox_send 失败，到期回查应转 PAID；恢复后通知仍投递 |
| 关闭先于支付确认 | 到期关闭后调用模拟成功应 409，支付保持 CLOSED |
| 关单响应丢失 | after_close_commit 延迟超过 RPC 截止，再阻断回查；未知期间保留 CLOSING/LOCKED，恢复后释放 |
| 库存确认失败 | before_confirm 阻断，观察 PAID/LOCKED 且不可履约，清理故障后 CONFIRMED |
| 库存释放失败 | before_release 阻断，观察 CANCELED/LOCKED，恢复后 RELEASED |
| 服务退出 | 在交易订单提交后主动退出，检查 bootId 变化、稳定业务键及恢复后的唯一订单 |
| 消息乱序 | 真实释放先到、迟到预占被墓碑拒绝；重复投递到期事件保持终态和库存守恒 |

四个额外窗口为：预扣后落库前退出、Broker 已收而本地发送结果丢失、支付创建/关闭并发、Redis 重建与旧在途请求竞争。窗口测试通过真实业务方法和故障点构造，不返回伪造成功响应。

故障点由当前实例运营接口设置，只允许已注册位置；规则默认一分钟、最多五分钟，支持 fail/delay/crash。交易支持 after_prehold、after_accept_commit、after_order_commit、before_outbox_send、after_outbox_send；支付支持 before_query、after_create_commit、after_close_commit、before_outbox_send、after_outbox_send；商品支持 before_reserve/confirm/release 和 after_reserve/confirm/release_commit。完整名称带 trade./payment./catalog. 前缀。规则不跨实例同步，服务退出后清空；验收会定向注入并检查命中或 bootId。

每次真实执行在 `.cache/reports/<UTC时间>/` 写 report.json 与 http.jsonl，记录配置、场景开始时间、耗时、请求步骤、注入参数、状态、traceId、最终事实及不变量错误；不保存登录密码、Bearer 头或登录返回的 JWT。等待有 30 秒上限，超时保存诊断及队列记录并判失败。HTTP 报告不能替代数据库诊断，也不证明未测环境或 M3 多 Pod 行为。

业务静止、已到期工作收敛后独立运行：

```bash
docker compose -f compose.yaml -f compose.acceptance.yaml run --rm diagnose
```

diagnose 分别读取三库，核对订单、支付、库存流水、额度、资格和快照，报告到期积压、Inbox 未完成及 NEEDS_REVIEW；未来执行的到期任务不误报为积压。演示夹具会保留释放墓碑及支付竞争记录，按稳定业务键可追溯；脚本不删除这些事实。
