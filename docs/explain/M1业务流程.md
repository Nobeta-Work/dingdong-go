# M1 业务流程：从登录、受理到支付与超时恢复

更新于 2026-10-26。本篇以 M1 建立的业务规则为主，按当前 M2 源码解释实际入口和调度方式；历史机制明确标注 M1，不要求在当前源码中寻找已经替换的旧函数。先理解业务，再到 M2.md 学习并发与恢复。本文不是运行验收报告，本次没有启动服务、调用交易接口或修改数据库。

先读 [框架](框架.md) 理解目录和 Configure/Runtime，再按本篇追踪业务。RPC 基础见 [grpc.md](grpc.md)，完整 URL 和返回字段见 [API.md](../../API.md)。命令统一使用 Bash。

## 1. 先分清六类状态

| 对象 | 主要状态 | 它回答的问题 |
| --- | --- | --- |
| 活动 | DRAFT、PUBLISHING、PUBLISHED、PAUSED | 是否已发布、是否接受新请求 |
| 受理 | ACCEPTED、PROCESSING、ORDER_CREATED、FAILED | 本次请求处理到哪里 |
| 参与资格 | AVAILABLE、HELD、CONSUMED | 当前用户能否再次参与这个活动 |
| 订单 | PENDING_PAYMENT、CLOSING、PAID、CANCELED | 交易是否已支付或关闭 |
| 库存预占 | LOCKED、CONFIRMED、RELEASED | 对应商品是否被锁定、售出或释放 |
| 支付单 | PENDING、SUCCESS、CLOSED | 支付服务掌握的支付事实 |

活动还有按时间计算的 phase：UPCOMING、ACTIVE、ENDED。它与发布状态并列，不能仅看到 ACTIVE 就认定允许参与，submit 还要检查 PUBLISHED。

```text
受理：ACCEPTED → PROCESSING → ORDER_CREATED
                          └→ FAILED
资格：AVAILABLE → HELD → CONSUMED
                    └→ AVAILABLE（仅成单前最终失败）
订单：PENDING_PAYMENT → PAID
                    └→ CLOSING → PAID / CANCELED
预占：LOCKED → CONFIRMED / RELEASED
支付：PENDING → SUCCESS / CLOSED
```

预占允许直接创建 RELEASED 标记，支付允许直接创建 CLOSED 标记，以阻止迟到操作。成单后的取消不恢复活动资格和已用额度，只释放 SKU 库存。

因此“请求已返回订单号”“支付接口成功”“订单已支付”“库存已确认”是不同事实，前端不能混成一个布尔值。代码只在 PAID 且 inventoryStatus=CONFIRMED 时计算 fulfillable=true。

## 2. 登录与可信身份

源码：internal/user/http.go、internal/platform/auth/auth.go。

POST /api/auth/login 绑定用户名和密码，查询 users，使用 bcrypt.CompareHashAndPassword 比对哈希，再调用 auth.Token 签发两小时 HS256 JWT。Claims 使用 subject 保存用户 ID，role 保存 USER/OPERATOR，issuer 固定 dingdong。

auth.Require 由各 HTTP 服务独立执行：验证 Bearer 格式、签名算法、issuer、有效期、用户 ID 和角色，再将可信 userId/role 放入 Gin context。运营接口要求 OPERATOR。

资源归属还需二次检查：即使 token 有效，也不能查询或支付别人的订单。交易和支付代码从自身数据库读取归属，与验签上下文比较；客户端不能通过传 userId 改变归属。

## 3. 创建草稿、发布和暂停

源码：[trade/activity.go](../../internal/trade/activity.go)、[admission.go](../../internal/trade/admission.go)。

createActivity 检查时间范围，RPC 查询商品，检查启用状态，保存 SKU ID、名称快照和运营传入的价格、额度、开始/结束时间。活动价是运营提交的 priceCent，不是自动复制商品原价。

M1 的核心发布规则是 DRAFT→PUBLISHING→PUBLISHED，发布额度不能超过当时可用 SKU 库存；失败保留 PUBLISHING 可重试，成功重放不重置额度。

当前 M2 还要建立 Redis 准入镜像：publish 校验 SKU 后，scheduleRebuild 持久化代次与恢复任务，buildAdmission 分页构建并验证快照，SQL 将发布中转 PUBLISHED、准入转 ACTIVE，最后激活 Redis ready。PUBLISHED 但镜像缺失时，重复发布也可能触发恢复，不应只检查业务 status。

pause 事务内锁活动，将 PUBLISHED/PAUSED 保持为 PAUSED，递增 admission_revision 并写缓存失效任务。它阻止新受理，不取消已持久化请求，也不恢复已消耗资格。即便 Redis 元数据或展示缓存暂旧，SQL 最终受理仍检查 PAUSED 并拒绝。

当前已新增只改展示标题的 PATCH 接口，不修改已发布活动的 SKU、价格、额度等交易字段。

发布时的查询不是 SKU 锁定。多个活动可竞争同一库存，真正成单时还要 Reserve 原子预占；合法受理不保证订单必然成功。

## 4. 受理：HTTP 请求到达与持久化承诺的区别

源码：[request.go](../../internal/trade/request.go)、[http.go](../../internal/trade/http.go)、[rate.go](../../internal/trade/rate.go)。

### 4.1 稳定身份与请求幂等

requestId 允许一到六十四位字母、数字、下划线或短横线。activityId 归一化后，对 activityID+":1" 计算 SHA-256，1 表示当前固定数量。

同一用户+requestId 是请求幂等范围，数据库唯一键也覆盖它。相同参数返回旧结果；换活动参数返回 409。相同 requestId 可以在不同用户中各自使用，但归属由已验签 userId 决定。

换新 requestId 不能绕过同活动资格：AVAILABLE 才能占用，HELD/CONSUMED 都不允许新受理，订单表还有 activityId+userId 唯一约束。

### 4.2 M1 与当前执行入口的区别

M1 最初在旧请求重放后仅做 Redis PING，再直接进入数据库准入。当前 M2 不再使用这条入口：requestLimit 先重放、扣用户与活动桶，submit 再重放并调用 Lua 预扣，得到 ticket 后才调用 persistTicket。

预扣只是 Redis 临时占活动额度，不是数据库受理，更没有锁定 catalog SKU。未通过 persistTicket 前不会返回新受理 202；代次重建、限流或依赖错误可能先返回 409/429/503。

已持久化请求重放在限流和预扣前，所以原请求不会因为令牌耗尽或 Redis 暂不可用再次扣额度。限流和预扣细节放在 [M2](M2.md)，先抓住后面的数据库承诺。

### 4.3 当前最终受理事务

```text
BeginTx（READ COMMITTED）
  → 锁活动行 SELECT ... FOR UPDATE
  → 再查同用户同 requestId 原结果
  → 检查 SQL ACTIVE、ticket epoch、version 一致
  → 检查 PUBLISHED、有效时间、used_quota < quota
  → 锁用户活动资格，要求 AVAILABLE
  → 保存 ticket 中固定 orderNo、活动快照和 ACCEPTED
  → 资格 HELD，记录 holder_request_id
  → used_quota+1，admission_revision+1
  → 写 CreateOrderRequested Outbox
  → 写十秒后成单兜底任务和 AcknowledgeAdmission
Commit → 新受理 HTTP 202
```

数据库锁和唯一约束没有因为 Redis 而消失。M2 过滤并发流量，但最终持久化裁决仍在 SQL。

明确拒绝会持久化 FAILED、失败原因与 RefundAdmission 任务后返回冲突；SQL 技术错误或提交未知不能直接当失败回补。当前 HTTP 返回 409 后，可能已有可查询的 FAILED 事实。

202 的意思是请求已持久化。返回的 orderNo 已固定，但 orders 表可能还没记录；客户端先按 requestId 查询，等 ORDER_CREATED 再按 orderNo 查询订单或申请支付。

## 5. 业务提交后，事件怎样推进后续动作

源码：[event/bus.go](../../internal/platform/event/bus.go)、[work/queue.go](../../internal/platform/work/queue.go)、[worker.go](../../internal/trade/worker.go)。

### 5.1 Outbox 与业务同事务

event.Put 接收业务 *sql.Tx，写当前服务的 outbox。受理与成单事件同事务，支付成功与成功事件同事务，订单终态与库存收尾事件同事务。

eventId 从事件类型+aggregateID 生成确定性 UUID。重投同一动作使用同一 eventId；重复 Put 不重置 SENT。这是当前“一订单一种终态动作”的模型约定，不是所有事件都能按类型和对象永久去重。

### 5.2 当前 M2 的真实消费链

```text
Outbox 工作者 SendSync → Broker 确认后 SENT
  → MQ 回调保存原消息到 event_inbox
  → 保存成功即可 ACK，失败请求 Broker 重投
  → Inbox 工作者调用 handleEvent，将事件写入 operation_task
  → 任务工作者 handleTask，执行 createOrder/closeOrder 等业务
```

M1 曾在 SDK 回调直接调用业务；当前不再这样。Inbox DONE 表示可靠转交任务，不表示订单已经完成。Outbox SENT 也只表示 Broker 确认，不表示接收方已成功处理。

payment 的 Bus 只发 Outbox；trade 拥有 Outbox、Inbox 和操作任务队列。坏消息仍保留原文，处理失败进入有界重试和 NEEDS_REVIEW，而不是解析失败就丢弃。

### 5.3 业务层只需认识事件对应动作

| 事件 | 写入方 | 最终执行的业务方法 |
| --- | --- | --- |
| CreateOrderRequested | trade.persistTicket | createOrder |
| PaymentSucceeded | payment.simulate | paymentSucceeded |
| InventoryConfirmRequested | trade.finishOrder | settleInventory(confirm=true) |
| InventoryReleaseRequested | trade.finishOrder/failRequest | settleInventory(confirm=false) |
| OrderExpiryDue | trade.createOrder | closeOrder |

受理、建单和订单终态还同事务保存本地延后兜底任务；正常消息到达可提前唤醒它，不会再创建另一张订单。

### 5.4 重复和退出时靠什么继续

Broker 已接收而本地 SENT 未保存时可重发；Inbox 同 eventId 重复到达只增加 deliveries；同业务键+动作任务去重；业务本身再检查订单/预占/支付终态。

当前统一队列使用十五秒租约、每次领取新 token、十秒处理预算、有限指数退避和人工恢复。详细竞争过程见 M2，不能再按旧版的三十秒进程 owner 或无限扫描理解。

## 6. createOrder：RPC 预占后再生成本地订单

源码：trade/order.go；库存实现为 catalog/inventory.go。

先读受理与快照；ORDER_CREATED/FAILED 为终态，重复消费不再建单。将 ACCEPTED 改 PROCESSING，按固定 orderNo、快照 SKU、quantity=1 调用 Reserve。

### 6.1 库存事务里的关键细节

Reserve/Release 共用 change：先插入或识别相同 order_no+sku_id 流水，再 FOR UPDATE 读取。仅首次 Reserve 执行条件更新：SKU 启用且 available>=1 才 available-1、locked+1；失败返回 ResourceExhausted，整个事务回滚。

重复 Reserve 不二次扣减，数量不一致或已 RELEASED 返回明确拒绝。Confirm 将 locked 转 sold；Release 将 locked 转回 available。库存表 CHECK 约束要求非负且 available+locked+sold=total，流水和计数在一个本地事务内变化。

app 明确设置 MySQL ClientFoundRows=false，因为 change 用 RowsAffected 区分首次插入与重复无变化调用。这个配置是实际算法依赖，不是无关优化。

Release 先到时插入 RELEASED 标记，不增加 available；它表示“这个键禁止以后预占”，不表示真的释放了曾经扣减的库存。迟到 Reserve 读到标记后拒绝。

### 6.2 结果未知与最终失败

ResourceExhausted 或 FailedPrecondition 属于当前明确拒绝，进入 failRequest。其他错误先按相同业务键 GetReservation：观察到 LOCKED/CONFIRMED 可以继续，RELEASED 视为终止，查询仍失败则保留 PROCESSING，让消息重投/扫描恢复。

failRequest 锁活动与请求，把受理记 FAILED；只有 holder_request_id 仍匹配当前请求且状态为 HELD，才退回资格并 used_quota-1，同时写库存释放事件、InventoryReleaseRequested 兜底任务和 RefundAdmission。旧失败请求仍返回旧失败结果，不会因为资格恢复而自行重生。

未知错误不直接判 FAILED，否则可能把已成功预占的请求当失败，并错误发放新资格。

### 6.3 本地建单事务

预占确定成功后，交易库事务锁受理并再次检查终态，然后插入 orders、order_items，将资格 HELD→CONSUMED、受理→ORDER_CREATED，同时写 OrderExpiryDue Outbox 和 expiresAt+5秒的同动作兜底任务后提交。

订单金额与商品名称来自受理快照，不临时重新查询覆盖。支付截止时间在此时按 now+PAYMENT_WINDOW 固定，精确到毫秒。合法受理即使排队跨过活动结束时间，仍可按快照建单，不重新否决活动时间。

库存 RPC 与交易建单不在同一事务：如果库存已锁但交易提交失败，重试复用同一业务键，扫描也能从 PROCESSING 继续推进。

## 7. 支付：成功事实与可履约是两步

源码：trade/order.go、payment/payment.go。

### 7.1 创建或获取支付单

trade.createPayment 先读订单，验证归属、PENDING_PAYMENT 和 expiresAt，再 RPC CreateOrGet，金额、用户和截止时间来自订单，不接收客户端随意指定。

payment 以 order_no 唯一，事务内插入并锁定读取，核对同键参数一致。重复创建返回原支付单，已 CLOSED 不被覆盖。RPC 不确定失败时 trade 回查 QueryByOrder 并核对事实。

### 7.2 模拟成功

payment.simulate 锁支付单，核对归属、未关闭、未过期，将 PENDING→SUCCESS；同事务 Put PaymentSucceeded。重复成功仍尝试写同一确定性事件键，不会生成另一份成功动作，也不会重置已发送状态。

这里只模拟支付，没有真实扣款。HTTP 返回成功表示支付服务持久化成功，不代表交易库和库存已同步完成。

### 7.3 支付事件如何转成已支付订单

trade.paymentSucceeded 收到事件后先 RPC QueryByOrder，不仅信任消息本身；确认 SUCCESS，核对用户与金额，再 finishOrder。

finishOrder 锁订单，将状态转 PAID，并在同事务写 InventoryConfirmRequested Outbox 与五秒后兜底任务。事件经 Inbox 转任务后，或兜底任务到时，由 handleTask 调 settleInventory→Confirm，成功或回查确认目标状态后，才更新交易库 inventory_status=CONFIRMED。

```text
payment.SUCCESS
  → PaymentSucceeded
  → trade.PAID + InventoryConfirmRequested
  → catalog.CONFIRMED
  → trade.inventory_status=CONFIRMED
  → fulfillable=true
```

短暂出现 PAID+LOCKED 是允许的中间态，查询端不能提前展示为可履约。

## 8. 超时关闭：先裁决支付，再释放库存

源码：trade/order.go 的 closeOrder、payment/payment.go 的 CloseByOrder。

OrderExpiryDue 到期投递或恢复扫描触发 closeOrder。未到期返回，终态 PAID/CANCELED 直接返回，其余到期订单从 PENDING_PAYMENT 条件转 CLOSING。

```text
CLOSING → QueryByOrder
  ├─ SUCCESS → paymentSucceeded → PAID → 确认库存
  ├─ NotFound / PENDING → CloseByOrder
  │                         ├─ SUCCESS → 同上
  │                         └─ CLOSED → CANCELED → 释放库存
  └─ 超时/依赖异常/未知状态 → 保留中间态，等待重试
```

不能把 QueryByOrder 的 NotFound 当成“可以直接释放”：迟到的 CreateOrGet 可能正在路上，所以还要 CloseByOrder 写 CLOSED 标记。以后同 orderNo 的创建不能覆盖该标记。

支付成功和关闭在 payment 本地事务内锁同一支付事实，SUCCESS/CLOSED 互斥。交易 finishOrder 也拒绝相互矛盾的终态。RPC 返回未知时不会猜测 CLOSED。

CANCELED 与释放事件同事务提交；实际释放成功后交易 inventory_status 再变 RELEASED。取消不减少活动 used_quota，不恢复 CONSUMED 资格，这与成单前 FAILED 的处理不同。

## 9. 到期提醒、兜底任务和恢复扫描

OrderExpiryDue 的 Outbox next_attempt_at=expiresAt，到期后才发送；本地同动作兜底任务排在 expiresAt+5秒。不是每张订单一个内存 timer，也没有使用 Broker 原生延时消息。

当前 [worker.go](../../internal/trade/worker.go) 的 recoverLoop 每五秒运行 scanBusiness 和 scanAdmission。扫描负责发现/补齐工作，网络动作由队列执行：

| 当前扫描 | 检查事实 | 补齐或安排 |
| --- | --- | --- |
| scanBusiness 请求页 | 超十秒 ACCEPTED/PROCESSING | CreateOrderRequested |
| scanBusiness 订单页 | 到期 PENDING_PAYMENT/CLOSING | OrderExpiryDue |
| scanBusiness 订单页 | PAID/CANCELED 仍 LOCKED | InventoryConfirmRequested/InventoryReleaseRequested |
| scanAdmission 活动页 | 代次/哨兵/ready 不完整 | scheduleRebuild |
| scanAdmission pending | 超五秒未确认预扣 | 先按 SQL 终态安排 ACK/REFUND |

各类查询按游标分页，避免一次读全表；页尾游标归零，后续重新发现遗留状态。五秒是触发间隔，不是任何故障的完成承诺。

M1 旧版 scanRequests/scanOrders/scanTasks 直接跑业务，RELEASE_BEFORE_ORDER 也是旧任务名。M2 迁移把它转换为 InventoryReleaseRequested，当前任务包含成单、关单、库存动作、缓存失效、准入确认/回补/重建。

work.PutTask 对 PENDING 可提前时间，不把 DONE 或 NEEDS_REVIEW 变回待办。因此恢复扫描不是绕过重试上限的隐藏循环；达到人工检查状态后，需要修复原因并显式 retry。

## 10. 用 Bash 观察一条支付链路

已有自动演示优先使用 `bash scripts/demo.sh --scenario pay` 或 `bash scripts/demo.sh --scenario timeout`，它们调用真实接口并检查归属/幂等与终态。以下展开手动步骤，便于把请求与源码对应；遇到 429/503 或准入重建时先检查依赖与状态，不要跳过失败继续执行。

以下步骤供后续手动操作，本次未执行。前提：服务已启动、迁移和种子完成；Bash 环境有 curl、jq、GNU date。命令会创建活动、消耗真实 Demo 库存，应在本地演示环境执行。jq 仅是命令行查看 JSON 的工具，不是项目 Go 依赖。

先输入初始化种子时使用的密码，不自动执行或 source .env：

```bash
read -r -s -p '种子账号密码: ' DEMO_PASSWORD
printf '\n'
USER_API='http://localhost:18080'
TRADE_API='http://localhost:18082'
PAYMENT_API='http://localhost:18083'

# -f 使 HTTP 错误以非零退出；每步确认成功后继续。
login_body=$(jq -n --arg password "$DEMO_PASSWORD" '{username:"operator",password:$password}')
OPERATOR_TOKEN=$(curl -fsS -H 'Content-Type: application/json' \
  -d "$login_body" "$USER_API/api/auth/login" | jq -er '.data.accessToken')
login_body=$(jq -n --arg password "$DEMO_PASSWORD" '{username:"user01",password:$password}')
USER_TOKEN=$(curl -fsS -H 'Content-Type: application/json' \
  -d "$login_body" "$USER_API/api/auth/login" | jq -er '.data.accessToken')
unset DEMO_PASSWORD login_body
```

新建已开始、尚未结束的活动并发布。下面的 GNU date -d 可用于 Linux/WSL 和常见 Git Bash 环境：

```bash
now=$(date +%s)
starts_at=$(date -u -d "@$((now - 60))" '+%Y-%m-%dT%H:%M:%SZ')

  -H 'Content-Type: application/json' -d "$body" \
  "$TRADE_API/api/admin/activities" | jq -er '.data.id')
curl -fsS -X POST -H "Authorization: Bearer $OPERATOR_TOKEN" \
  "$TRADE_API/api/admin/activities/$ACTIVITY_ID/publish" | jq
```

提交受理并查询。保留同一个 REQUEST_ID，用来观察幂等重放：

```bash
REQUEST_ID="learn-$(date +%s)-$RANDOM"
body=$(jq -n --arg id "$REQUEST_ID" '{requestId:$id}')
curl -fsS -H "Authorization: Bearer $USER_TOKEN" \
  -H 'Content-Type: application/json' -d "$body" \
  "$TRADE_API/api/activities/$ACTIVITY_ID/requests" | jq
# 查询至 status=ORDER_CREATED；若 FAILED，先阅读 failureReason。
curl -fsS -H "Authorization: Bearer $USER_TOKEN" \
  "$TRADE_API/api/requests/$REQUEST_ID" | jq
```

上一条看到 ORDER_CREATED 后再执行；没有完成时不要仅凭返回了 orderNo 就跳到支付：

```bash
ORDER_NO=$(curl -fsS -H "Authorization: Bearer $USER_TOKEN" \
  "$TRADE_API/api/requests/$REQUEST_ID" \
  | jq -er '.data | select(.status=="ORDER_CREATED") | .orderNo')
PAYMENT_NO=$(curl -fsS -X POST -H "Authorization: Bearer $USER_TOKEN" \
  "$TRADE_API/api/orders/$ORDER_NO/payment" | jq -er '.data.paymentNo')
curl -fsS -X POST -H "Authorization: Bearer $USER_TOKEN" \
  "$PAYMENT_API/api/payments/$PAYMENT_NO/simulate-success" | jq
# 继续观察，直到 PAID、CONFIRMED、fulfillable=true。
curl -fsS -H "Authorization: Bearer $USER_TOKEN" \
  "$TRADE_API/api/orders/$ORDER_NO" | jq
```

这些命令按步骤手动执行，不是完整自动验收脚本；任何一步失败应停止并检查响应/日志。支付窗口从订单生成开始计时，手动操作太慢会被正常关闭，不能再强行补付；如需重演应创建新活动和新请求。

超时路径可创建另一活动并受理，在成单后不调用 simulate-success，按订单 expiresAt 等待并查询，直到 CANCELED+RELEASED。既可创建支付单后不付，也可完全不创建支付单；后一种用于观察关闭标记。不要沿用已成功订单模拟关闭，也不要用删除数据卷重置。

## 11. 怎样判断流程收敛

| 路径 | 交易库 | 支付库 | 商品库 |
| --- | --- | --- | --- |
| 成功 | PAID、CONFIRMED、fulfillable=true | SUCCESS，用户/金额匹配 | 预占 CONFIRMED，locked 转 sold |
| 超时取消 | CANCELED、RELEASED | CLOSED，允许无 paymentNo 的关闭标记 | 预占 RELEASED，locked 回 available |
| 成单前最终失败 | request=FAILED，资格按持有者释放，额度退回 | 通常没有支付单 | 已有锁定释放，或存在 RELEASED 终止标记 |

业务静止、恢复动作完成后，可以使用只读诊断：

```bash
docker compose run --rm diagnose
```

diagnose 分别读取各库，在内存核对库存非负/守恒/流水、订单支付与预占终态、订单唯一与快照、资格和额度、未完成受理、已到期积压及 NEEDS_REVIEW。尚未到期的未来任务不应当作积压。它可能指出“未收敛”，不负责自动修复；执行期间继续交易会使跨服务读到不同时间的事实。

日志可按 requestId、orderNo、eventId、traceId 关联。当前 traceId 会进入事件信封与任务，HTTP/任务 ctx 中的追踪号也由 RPC 客户端 interceptor 传为 x-trace-id；服务端失败日志读取该字段。恢复扫描可能使用 recovery 标记，当前仍不等于接入完整分布式 tracing 平台。

## 12. 事务与故障处理的核心取舍

1. 数据库事务只覆盖本服务；跨服务靠业务键、消息与恢复流程衔接。
2. 写操作超时表示结果未知，先回查，不把未知伪装成缺货或关闭成功。
3. 业务结果与下一步事件同事务持久化，发送过程允许重复。
4. 成单前失败可以退资格和额度；成单后取消仅释放库存，两者规则不同。
5. 先写终止标记能阻挡迟到创建，单纯查询“现在不存在”不够。
6. 持久化扫描恢复中间态，不能把进程内定时器当作唯一可靠依据。

M1 业务主线仍需真实运行验收。当前 M2 已补齐 Redis Lua 准入、缓存、有界重试/NEEDS_REVIEW、统一任务领取和故障并发验收工具；这些能力的原理及操作见 M2.md，不能继续讲成尚未开发，也不能因工具存在就认定验收已通过。

## 13. 把一笔订单的数量变化写出来

设 SKU total=200、活动 quota=1、用户 U 第一次参与，没有其他交易竞争。以下是已完成相应阶段后的示意快照，异步动作之间可能短暂不同步。

| 阶段 | 活动 used_quota | SQL 资格 | SKU available/locked/sold | 请求/订单 |
| --- | --- | --- | --- | --- |
| 开始 | 0 | 无记录或 AVAILABLE | 200/0/0 | 无 |
| Redis 预扣（M2） | 0 | 仍未正式 HELD | 200/0/0 | 只有 ticket，无 SQL ACCEPTED |
| SQL 受理提交 | 1 | HELD | 200/0/0 | ACCEPTED，已有固定 orderNo |
| 真实库存预占 | 1 | HELD | 199/1/0 | PROCESSING，可能尚未建订单 |
| 建单提交 | 1 | CONSUMED | 199/1/0 | ORDER_CREATED、PENDING_PAYMENT |
| 支付路径收敛 | 1 | CONSUMED | 199/0/1 | PAID、CONFIRMED |
| 若走超时路径收敛 | 1 | CONSUMED | 200/0/0 | CANCELED、RELEASED |

最后两行是二选一，不是同一张订单先支付再取消。超时释放后 SKU 可被别的合法订单使用，但 U 在这个活动仍不能再下单，quota 也不会重新变成一份可参与额度。

成单前最终失败是另一条路径：只要当前 HELD 仍由这次 requestId 持有，used_quota 可从1退回0、资格回 AVAILABLE，预占释放或写终止标记；M2 还异步回补 Redis。旧 requestId 保持 FAILED，尝试新参与必须用新 requestId。

## 14. 对照源码时按事务边界读

| 先找的方法 | 本地事务关键事实 | 事务外/跨服务动作 |
| --- | --- | --- |
| persistTicket | 请求、资格、额度、Outbox、任务 | Lua 预扣在此前完成 |
| inventory.change/Confirm | 库存计数与预占流水 | 不直接改交易库 |
| createOrder | orders、items、资格消耗、请求终态、到期事件/任务 | Reserve 在交易事务之前 |
| payment.simulate | SUCCESS 与 PaymentSucceeded | 消费和库存确认在提交之后 |
| finishOrder | PAID/CANCELED 与库存收尾事件/任务 | Confirm/Release 由任务推进 |
| closeOrder | 条件转 CLOSING；终态另有本地事务 | QueryByOrder/CloseByOrder 无法纳入交易库事务 |

每次看到 tx.Commit 都问：返回失败时是否可能已经提交？下一次调用会按什么唯一键查询？每次看到 RPC 都问：对方成功但响应丢失时，本端是否会错误退款或重新分配业务键？
